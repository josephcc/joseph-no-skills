# Data model

One analysis folder per study, conventionally `<study>/analysis/`, sitting beside the recording
folders that `watch-recording` produced. Four data files, one memo file, two output folders:

```
analysis/
├── study.yaml        roster + transcripts + analytic stance          (hand-edited, small)
├── codebook.yaml     codes, definitions, status, changelog            (hand-edited, small)
├── extracts.jsonl    every coded extract, one per line                (written by ta.py only)
├── themes.yaml       themes, the codes they gather, chosen quotes     (hand-edited)
├── inbox.jsonl       operations the researcher staged in the workbench (written by the browser only)
├── memos.md          dated analytic memos                             (append as you go)
├── reviews/          interactive-plan documents, one per negotiation round
│   ├── *-applied.jsonl   every operation `apply` executed, with its result (the review's audit trail)
│   └── annotated/    `annotate` output: each transcript with its coded spans highlighted (a text/PDF fallback
│                     for a co-author; the workbench's transcript view is the review surface)
├── audit/            optional: dated full output of coverage/dupes/verify runs worth keeping
└── reports/          generated by `ta.py report`; never edit by hand
```

Two files have exactly one writer, and that is the whole safety story: `extracts.jsonl` is
written only by `ta.py`, so a quote cannot be typed from memory; `inbox.jsonl` is written only
by the workbench, so the browser never touches an analysis file. `ta.py apply` is where the two
meet.

The script rewrites `study.yaml`, `codebook.yaml`, and `themes.yaml` when it changes them
(`mark-coded`, `bump`, `merge-code`, ...), and a rewrite does not preserve `#` comments. Put notes
in `notes:` fields, `include`/`exclude`, the changelog, or `memos.md`, never in YAML comments.

Why four files and not one: the two the human reviews (codebook, themes) stay small and
git-diffable; the one that grows to thousands of lines (extracts) is append-friendly and
greppable; the roster changes least and is the thing every other file resolves against.

Why `extracts.jsonl` is written only by the script: the extract command copies the quote out of
the transcript at the line you name. Text that never passed through a model cannot be
hallucinated, misremembered, or quietly tidied. Everything downstream (themes, quote bank, paper
draft) references extracts by id, and `verify` re-checks all of them against the transcripts on
demand.

## `study.yaml`

```yaml
study: Cocoa lab study
approach:
  orientation: hybrid           # inductive | deductive | hybrid
  level: semantic               # semantic | latent
  epistemology: realist         # realist | contextualist | constructionist
  prevalence_unit: participant  # the one unit prevalence is counted in (Braun & Clarke: be consistent)
  notes: >
    Wording the method section can reuse: what drove the coding, what the codes were about.
research_questions:
  - id: RQ1
    text: How does co-planning change how researchers steer an agent?
participants:
  - id: P1                      # the id the paper will use. Groups: H1..Hn / N1..Nn; deployment: D1..
    role: participant           # participant | interviewer | researcher | other
    speakers: [Alice Example, SPEAKER_01]   # every label this person has in any transcript
    group: HCI                  # optional
    notes: PhD student, used the system for 3 days   # optional
  - id: INT
    role: interviewer
    speakers: [Joseph Chang]
transcripts:
  - id: T-01
    path: ../recordings/p1/transcript.md   # relative to analysis/, or absolute
    participants: [P1]
    kind: interview             # interview | think-aloud | mixed | diary | other
    coded_with_version: 2       # codebook version this transcript was last fully coded with; null = uncoded
```

`init` seeds this from the speaker labels it finds. Placeholder ids (`TODO-...`) and
`role: unknown` fail `validate` on purpose: deciding who is a participant is an analytic act.
Speech from anyone whose role is not `participant` is context, never data, and `extract`
refuses it unless told otherwise.

## `codebook.yaml`

```yaml
version: 4            # bumped by merge-code and bump; extracts and transcripts record the version they saw
frozen: false         # set true (bump --freeze) once the last interview is coded; later changes force re-coding
codes:
  - id: control                       # kebab-case. A child is `parent.child`. Two levels, never three.
    name: Sense of control over the agent
    parent: null
    definition: >
      Participant describes steering, fixing, or redirecting the agent's work, or the felt
      absence of that ability.
    include: Editing/rerunning steps, deleting outputs, choosing execution mode.
    exclude: Complaints about output *quality* with no reference to steering (-> quality).
    status: accepted                  # candidate | accepted | merged | retired
    merged_into: null
    tags: [RQ1]
    examples: [E-0003, E-0041]        # 1-3 canonical extracts; codebook-table prints the first
    added: {version: 1, date: 2026-08-14, source: "P1 review"}
    redefined_version: 3              # set when definition/include/exclude changed; drives `stale`
    reviewed: {at: ..., version: 3}   # the researcher accepted or passed over it at this version
    proposal:                         # the agent's case for a candidate, shown beside the definition
      why: >
        Why this is not an existing code, in the words the review document quotes.
      alternatives: "make it trust.verification (child)"
      borderline: [E-0031]
      round: 3
  - id: control.rerun
    name: Rerunning or editing a step
    parent: control
    definition: ...
    status: accepted
changelog:
  - {version: 2, date: 2026-08-20, change: "accepted control.rerun (Q-C-control-rerun); merged agent-steering into control"}
```

Statuses: a `candidate` code was proposed by the agent and not yet accepted by the user; an
`accepted` code is in the codebook; a `merged` code keeps its id so old references resolve
(`merged_into`); a `retired` code is gone and `extract` refuses it. Every code with status
candidate or accepted needs a definition and should have `include`/`exclude` once it has a
neighbour it could be confused with. The definition is what a second coder would apply, so
write it as a rule, not a topic label.

## `extracts.jsonl`

One JSON object per line:

```json
{"id": "E-0041", "transcript": "T-01", "participant": "P1", "speaker": "Alice Example",
 "timestamp": "00:14:22", "line_start": 63, "line_end": 63,
 "text": "With the chat tool I would have to redo the whole prompt.",
 "codes": ["control.rerun"], "kind": "said", "context": "comparing to chat baseline",
 "note": null, "codebook_version": 2, "added": "2026-08-20"}
```

- `text` is verbatim from the transcript (whitespace collapsed, quotes straightened). Trim with
  `--from/--to`; never retype.
- `kind`: `said` (a stated view or experience), `did` (an action observed in a think-aloud or on
  a frame, or reported as done), `intent` (a modal-verb hypothetical: "I would probably use it
  for..."). The distinction comes from `watch-recording`: modal verbs are not actions, and a
  finding about what people *do* cannot rest on `intent` extracts.
- `context`: what the utterance is about when that is not obvious from the text (which condition,
  which task, which feature). In comparative studies this is what lets you separate "liked X" from
  "liked Y".
- `codes` may be empty temporarily (a passage worth keeping before its code exists), but
  `validate` warns until it is coded.
- `highlight` (optional): a short reason this extract is a candidate paper quote, set with
  `recode --highlight`. Not a selection; the quote bank lists flagged extracts above the per-theme
  selections so the theme round starts from what struck the researcher during coding.
- `reviewed` (optional): `{at, version}`, stamped when the researcher reviewed this extract in the
  workbench — either by acting on it or by pressing "Done with T-07", which stamps everything they
  left alone. Silence is acceptance, and the record is still complete.
- `updated` (optional): when an operation last changed this extract. An edit the *agent* made also
  drops `reviewed`, so the extract comes back as new; an edit the *researcher* made is itself a
  review. That is what "new since your last review" means, and it never depends on comparing two
  clock strings.

## `themes.yaml`

```yaml
themes:
  - id: TH1
    name: Co-planning afforded steerability       # a claim, not a topic
    parent: null                                  # sub-themes name their parent; two levels max
    rq: RQ1
    essence: >                                    # the two-sentence scope test (phase 5)
      Participants steered the agent by composing, editing, and rerunning plan steps, and read this
      as control they lacked in chat. The value was in intervening mid-process, not in better output.
    story: |                                      # the analytic narrative, markdown
      ...
    codes: [control, control.rerun, execution-mode]
    status: accepted                              # candidate | accepted | merged | dropped
    merged_into: null
    in_paper: headline                            # undecided | headline | secondary | no
    tensions: [E-0099]                            # extracts that complicate or contradict the theme
    selected_extracts: [E-0003, E-0041, E-0120]   # the quotes chosen for the paper, in order
    quote_spans:                                  # inline trims, sliced from the extract by the script
      E-0041: {text: "...", words: 17, from: being, to: step.}
    reviewed: {at: ..., version: 6}
```

`quote_spans` is how a long extract becomes a short inline quote without anybody retyping it:
`theme trim` (or the Quotes view) locates the researcher's selection inside the extract's own
stored text and saves the slice. The extract is untouched, the quote bank prints the trim and says
what it was cut from, and `verify-quotes` still passes on the draft.

Participants per theme are never stored; they are derived from the extracts carrying the theme's
codes, so the count in the paper can always be regenerated. `tensions` is not optional in spirit:
Braun & Clarke expect a pattern to have exceptions and expect the report to keep them.

## `inbox.jsonl`

One staged operation per line. The workbench appends here and nowhere else; `ta.py apply` executes
them, in the order they were staged, and moves each applied line to `reviews/<date>-applied.jsonl`
with its result.

```json
{"id": "op-0031", "at": "2026-09-02T14:12", "by": "user", "view": "transcript",
 "op": "recode", "target": "E-0042", "args": {"add": ["trust.stakes"], "remove": ["trust.generalised"]},
 "note": null, "status": "pending"}
```

- `op` is one of the names in `OP_SPECS` (`ta.py inbox --json` lists any that fail their schema).
  There is no free-text operation: a gesture the script cannot perform cannot be staged.
- `by` is `user` or `agent`. The agent stages its own structural proposals (`ta.py stage`) so a
  merge appears where its evidence is, and the researcher accepts or rejects it with one click.
- `status`: `pending` → `applying` (claimed by a running `apply`) → `applied` (archived) or
  `failed` (kept, with `error`, so nothing is lost — fix the cause and apply again). A malformed
  operation fails on its own; it never blocks the rest of the pass. A claim an `apply` died holding
  becomes `stalled` after fifteen minutes rather than being retried: whether it took effect is a
  question about the data, and re-running `new-extract` or `new-theme` blind would duplicate it. So
  `apply --all` skips a stalled row and `apply <id>` re-runs it deliberately — unless its id is
  already in an applied log, in which case the pass got that far and the row is simply cleared.
- `op: comment` is a thread, never applied. Replies are `op: reply` lines pointing at the thread's
  id; the researcher resolves it, as in the plan viewer, and `apply` archives resolved threads.
- An `edit-field` op carries the `old` text it was written against. If the definition moved in the
  meantime, `apply` refuses that one op and says so, instead of overwriting the newer wording.
- Ids are never reused, so `next_op_id` reads the inbox, every applied log, *and* the raw text of
  any line that would not parse — a truncated `{"id":"op-0042"…` has still spent that number. The
  daemon preserves such a line verbatim across its own rewrites for the same reason.
- Every command that rewrites a data file holds `analysis/.apply.lock` for its whole run and
  re-reads the files after taking it (`main` does this once, for every writing command, including
  `init --force` on a folder that already exists). Two writers loading, mutating and saving whole
  files from two snapshots would keep only the second one's work. A lock is stolen only when it is
  both older than fifteen minutes *and* its owning process is gone, so a slow or suspended writer
  keeps it. Stealing renames the stale file rather than deleting it, so of two contenders that both
  saw it only one wins; and a lock is released only by the process whose token is in the file, so a
  writer whose lock *was* stolen cannot delete its successor's. A lockfile from an older version of
  the script (a bare pid) is still understood well enough to check whether its owner is alive.
  These are cooperating local tools sharing an advisory lock, not mutually distrustful processes:
  the protocol makes the realistic races safe and says plainly what to delete when one goes wrong.
- Both inbox writers take a short lock (`.inbox.lock`) and every write is a full read-modify-write
  inside it. `apply` takes the lock three times: once to *claim* the operations it will run (so a
  second `apply` cannot take them and the daemon cannot rewrite them away), then not at all while
  it works, then once more to settle the file against a fresh read. An operation staged while it
  was working is therefore still there afterwards, and no writer has to reason about byte offsets
  in a file another one may have rewritten.

## Ids and history

Ids are stable and never reused. Merging or retiring keeps the old record with a status; the
changelog says when and why. `reviews/` keeps every negotiation document, so the path from a
participant's sentence to a published theme is reconstructible: transcript line → extract id →
code → theme → the review round where the user accepted it.

## What the audit commands check

| command | catches |
|---|---|
| `validate` | broken references, placeholder roster, a third code level, missing definitions/essences, selected quotes that carry none of their theme's codes |
| `verify` | an extract whose text is not verbatim at its locator; an extract attributed to the wrong participant (the turn's speaker resolves to someone else); coding of non-participant speech |
| `verify-quotes FILE.md` | any quote in a document (blockquote or inline, 5+ words) that is not verbatim in some transcript, allowing `[...]`/`[insertions]`; a quote attributed to a participant the transcript contradicts |
| `coverage` | codes nobody said, participants nobody coded, transcripts never coded or coded against an older codebook, per-theme n/N |
| `dupes` | two live codes with overlapping names, near-identical extract sets, or one a strict subset of the other |
| `stale` | transcripts that need a pass because the codebook changed since |
| `annotate T-01` | renders the coded transcript for review; overlapping spans on one turn get an empty anchor after the turn rather than nesting |
| `report` | regenerates `reports/`; archives any report that carries interactive-plan comments to `reviews/` first, so feedback left on a rendering is never lost |
| `validate` (added) | an extract whose text cannot be located inside its own turn (the workbench cannot highlight it); an inbox line that is not valid JSON or names an operation the script has no handler for |
| `inbox` | every pending operation, grouped by the view it came from, with the open threads beside them |
| `apply` | executes them, bumps the codebook once for the pass, stamps the codes whose meaning moved, then runs `stale`, `validate` and `verify` and prints the summary lines |
| `preflight` (used by `open`) | `validate` + `verify` + the inbox lint; `open` refuses to launch on an error, which is what `lint:plan` is to a hand-authored plan |
